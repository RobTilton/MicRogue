# Layout Interpretation Room DOTS
Updated: 2026-09-25

## Room Contract

- Room: `LayoutInterpretationRoom`
- Outcome: Build an encapsulated, generator-independent Layout Interpretation subsystem that accepts valid `MapData` plus a required family tag, claims useful semantic Zones from existing traversable geometry, records Zone metadata without placing content or changing map geometry, and exposes the completed result through a small public surface.
- Scope / prohibited territory: Define the family and Zone catalogs; analyze existing floor geometry; implement Zone claiming, ordered interpretation passes, coverage and fragment reconciliation; package interpretation metadata; expose and validate the subsystem; and maintain Room/current system documentation. Do not modify generated cell geometry or place doors, portals, stairs, traps, scenery, lighting, loot, actors, or other content. Do not depend on generator internals. Production writes require a later Box-specific Alignment Check and Rob's confirmation before promotion begins.
- Acceptance: A caller can provide any valid generator-independent `MapData` and a supported required family tag; the subsystem produces coherent Zone IDs, roles, tile membership, geometry and relationship metadata; universal and family-required Zone rules are applied in an explicit order; claimed tiles obey ownership invariants; coverage and irreducible leftovers are reported honestly; invalid or unsatisfiable inputs fail according to the approved contract; downstream systems can consume the result without knowing interpreter internals. Required automated checks pass, current-state/system documentation matches implementation, and human runtime/design acceptance remains recorded separately.
- Authority evidence: Rob established the system vision and four-stage traversal in conversation on 2026-09-25, approved the proposed Family Catalog -> Zone Catalog -> Claim and Zoning -> Package/Public Surface structure, and issued `Execute when ready` for Room setup.
- Starting state: The Production Map Generation System is documented as returning detached `MapData` with `width`, `height`, and row-major `cells` using `ABYSS = 0`, `FLOOR = 1`, and `WALL = 2`. The Room scaffold and Rob's [`FirstPassIdeation.md`](Documents/FirstPassIdeation.md) exist. No Layout Interpretation implementation or Git checkpoint has been established; Git checkpoint is unknown.

## Current References And Unresolved State

- [`Documents/FirstPassIdeation.md`](Documents/FirstPassIdeation.md) is Rob's initial concept draft and ideation evidence, not yet a final behavioral contract.
- `Tables/FamilyCatalog/`: family input language and initial family definitions.
- `Tables/ZoneCatalog/`: general, universal, family and fallback Zone definitions.
- `Tables/ClaimAndZoning/`: geometry analysis, atomic claiming, ordered passes, coverage and fragment reconciliation.
- `Tables/PackageAndSurface/`: interpretation data, public entry point and composed validation.
- `References/`: reserved for Room-local current-state and task references.
- `Outputs/`: reserved for retained Room outputs that do not belong in a Table.
- Confirmed design direction: callers provide a required family tag; Layout Interpretation owns the meaning and application of that tag. It claims and describes semantic Zones but never places their eventual contents.
- Confirmed minimum Spawn footprint: `3x2`, with `2x3` treated as the same shape under 90-degree rotation.
- Confirmed catalog method: candidate family spaces survive only when their identity materially changes a layout decision, such as required presence, geometry, relationship, route position, multiplicity, accessibility, or spatial reservation. Purely thematic distinctions belong to later systems.
- Family-aware optional/random selection is conditional, not presumed. Design it only if semantic reduction leaves enough meaningful non-universal optional roles to justify the mechanism; otherwise omit it.
- Proposed but not yet approved as final contracts: the initial family list and its exact Zone requirements; the `>= 85%` target; any optional-Zone selection mechanism; exact fragment thresholds; output attachment versus detached representation; deterministic/randomness guarantees; and unsatisfied-required-Zone failure behavior.
- Existing Map Generation documentation is an input contract reference, not authority to modify that system.
- Output disposition: retain Room documents and working outputs until explicit promotion or disposition authority is granted.
